# Development research for Copywriter

## Synopsis

**Copywriter** is a static website generator geared towards collaborative use by teams of copywriters.

## Problem that this solves

This project aims to be the statically generated solution to the same sort of experience that website software systems like Wordpress and Wikimedia provide for sites with little or no dynamic content.

We can define *dynamic content* here as data that is generated by someone or something other than the first-party content creators of a website:
- Users,
- external web services,
- internal systems running on a schedule, etc.

Whereas we can define *static content* here as data generated by the website's content creators, manually:
- Articles,
- product information,
- announcements,
- contact information, etc.

A common approach used by web-developers in setting up websites for a client with *static content* is to customize the software system (eg. Wordpress or Wikimedia). The web-developer "skins" the HTML (structure) and CSS (theme) of the system to match the client's branding and content requirements. Most importantly for the client, they then have access to a very simple interface for creating and editing content live.

The problem with this approach is that it requires a technology stack to always be available online just to *view* the website. The client inherits this maintenance burden.

With dynamic website systems, a webpage is never *just an HTML file*:
- A database server needs to be running. 
- A cache server needs to be running.
- Each webpage request from a browser invokes either a database query or a cache server query. 
- A server-side scripting language and environment must be available.
- A server-side scripting language package manager must be available.
- All server-side scripting language package dependencies must be available.
- Database server dies: Content is lost.
- Cache server dies: The website is slow.
- Cache becomes outdated: The wrong content is shown. 
- Server updates the scripting language improperly: Website goes offline.
- Restoring content from backup: Web developer required. 
- Transferring to a different hosting service:
  - The host must be running the *same* technology stack as above.
  - Web developer required. 
  
These requirements are acceptable for websites that provide dynamic content. However, this is **overkill** for sites that offer primarily static content.  

With a statically generated website, webpages essentially *are* just a bunch of HTML files. More accurately, they are a bunch of HTML, CSS, Javascript, and multimedia files stored in a directory structure. They can be zipped up as one, transferred, and unzipped onto just about any webserver without any other requirements. Copy and paste.

Static websites, however, are not easily edited for content. Therein lies the root of the problem that this project hopes to address: Website maintainers that would benefit from the simplicity of static generation need an easy way for content creators to edit content and an easy way to setup and maintain their websites.

This project does not present a radically new solution to this problem. There are currently several systems available that use the same or similar technologies. However, most of the systems reviewed so far are either very specific in scope as to what kind of content they provide or they are not designed for ease of use by people that are not web developers. Even if the maintainers are web developers, they are not necessarily interested in spending time and resources maintaining static websites. 

## This project's solution to the problem

We are going to integrate technologies and techniques that are common in the software development community in a way that is easy to use for content creators.

Collaborative editing and website source code will be managed by Git. Content creators will issue pull requests to submit new content once it is ready for review and publication. Authorship, versioning, and created/edited timestamps can be tracked automatically using Git. Access control is managed by the Git server offering the repository.

Content will be created using Markdown. Anyone that has used a bulletin board system or Reddit will be familiar with the format.

Website settings and content metadata will be stored as TOML. It's the simple `windows.ini` file format that is easy to read and write.

Templating will be done using Handlebars. It's well-known, easy-to-use, and works well. It's basically HTML with `{{data.title}}` where data needs to be shown.

Built-in metadata modeling will reflect well-known content standards that are search-engine optimized:
- OpenGraph (news, social media)
- Amazon and Ebay (product listings)

Website setup and management will be done using a single command-line tool: `copywriter`. It will be available on each major operating system and available on popular OS package managers (Linux, MacOS: HomeBrew, Windows: Chocolatey).

The technology stack on the server then boils down to:
- Webserver 

The technology stack for organization:
- Git server
- `copywriter` 

The technology stack for each content creator:
- Git
- `copywriter`
- Text editor
